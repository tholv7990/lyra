## Bundle gathering logic

For a project P with source workspace S, the bundle is:

1. All **tasks** with `projectId === P.id` and `workspaceId === S` (soft-delete filtered)
2. Union of `task.pipelines[]` across all tasks → pipeline IDs
3. **Pipelines** with `_id in pipelineIds` and `workspaceId === S`
4. Union of `step.promptId` across all pipeline steps → prompt IDs
5. **Prompts** with `_id in promptIds` and `workspaceId === S`

Keys are **never** included in the bundle.

## Transaction + conflict logic

### Conflict detection (blocks move)

Two kinds:

1. **Pipeline conflict** — a bundle pipeline is referenced by a task whose `projectId !== P.id` in the source workspace. This means another project the user keeps in personal also depends on that pipeline. Moving it would break the other project (cross-workspace references not allowed).

2. **Prompt conflict** — a bundle prompt is referenced by a pipeline whose `_id` is **not** in `pipelineIds` (i.e., a pipeline in S outside the bundle). Moving the prompt would break that other pipeline.

When any conflict exists, both `preview` and `transfer` surface them. The `transfer` endpoint additionally rejects with HTTP 400.

### Atomic move (Mongo transaction)

If no conflicts:
1. `connection.startSession()` + `session.withTransaction(fn)`
2. Inside the transaction:
   - `Project.findByIdAndUpdate` → set `workspaceId = target`, `status = 'public'`, `shared = 'all'`, `updatedBy = actorId`
   - `Task.updateMany` → set `workspaceId = target`
   - `Pipeline.updateMany` → set `workspaceId = target`
   - `Prompt.updateMany` → set `workspaceId = target`
3. `session.endSession()` in finally block

Keys are **never touched** — they remain scoped to the source personal workspace and the mover must add their own key to the team through the normal Settings flow.

### Permission validation (both endpoints)

In order:
1. `project.createdBy === userId` — only the creator can move (ForbiddenException)
2. Source workspace `type === WorkspaceType.Personal` (BadRequestException if team)
3. Target workspace exists and `type === WorkspaceType.Team` (BadRequestException)
4. User has an active membership in the target workspace (ForbiddenException)
5. Target membership `role !== Role.Viewer` — must be Member or Owner (ForbiddenException)

## Web flow

### `MoveToTeamModal.tsx` (`apps/web/src/components/`)

- Receives `projectId`, `teamWorkspaces` (pre-filtered to `WorkspaceType.Team`), `onClose`
- State: `targetId` (defaults to first team), `preview`, loading/error flags
- On `targetId` change: auto-calls `POST /projects/:id/transfer/preview` to populate the preview
- Renders:
  - Workspace selector (`<select>`)
  - Bundle summary: "N tasks · M pipelines · P prompts will move."
  - Keys warning (if `providers` minus `targetHasKeys` is non-empty): "The team needs keys for: X, Y"
  - Conflicts list (blocking, shown with name + reason)
  - One-way permanence warning (shown only when no conflicts): "This moves the project into <team> permanently…"
  - Confirm button: disabled when loading, no preview, or conflicts exist
- On confirm: `POST /projects/:id/transfer`, then `navigate('/projects')`
- Escape key closes modal

### `ProjectDetail.tsx` changes

- Imports `WorkspaceType`, `MoveToTeamModal`
- Destructures `workspaces` from `useWorkspace()`
- Derives `teamWorkspaces = workspaces.filter(w => w.type === WorkspaceType.Team)`
- Derives `canMoveToTeam = current?.type === WorkspaceType.Personal && user?.id === project?.createdBy.id && teamWorkspaces.length > 0`
- Adds `showMoveModal` boolean state
- Renders a `txt-btn` "Move to team" in `proj-meta` when `canMoveToTeam`
- Renders `<MoveToTeamModal>` when `showMoveModal`

## Concerns / limitations

1. **No e2e test for transfer itself** — the e2e suite doesn't cover `POST /projects/:id/transfer`. The unit tests cover all logic branches via mocks; a full e2e test would require two workspace setups (personal + team) and is deferred.

2. **`updatedAt` field** — the `$set: { updatedAt: now }` in the transaction may be ignored by Mongoose timestamps on some versions since `timestamps: true` controls that field. The `updatedBy` update is the authoritative audit trail; `updatedAt` will be refreshed by Mongoose on next save if the explicit set is ignored.

3. **Leaf moves (pipeline-only, prompt-only)** — the spec mentions `POST /pipelines/:id/transfer` and `POST /prompts/:id/transfer` for leaf moves. These are **not implemented** — only the project-bundle transfer is built. Leaf moves can be added later as separate controller methods.

4. **`common.cancel` i18n key** — the modal uses `t('common.cancel')` which must exist in the common locale. If it doesn't, it would silently fall back to the key string. The existing `RequestProviderModal` uses `t('settings.cancel')` — verified the common namespace has `cancel`.

## Security fixes (2026-06-20, commit `73e88ec6`)

### Finding A — task gather scoped to source workspace
`gatherBundle` now filters tasks with `workspaceId: sourceWorkspaceId` in addition to `projectId`. Previously a foreign task (belonging to a different workspace) could share the same `projectId` string and inject its pipeline ids into the bundle, allowing foreign pipelines/prompts to be swept into the move.

### Finding B — runs and assets re-pointed inside the transaction
The transaction now also moves Runs and Assets:

1. Before `runModel.updateMany`, a lean `find({ taskId: { $in: bundleTaskIds } }, { _id: 1 }, { session })` collects the run ids belonging to the bundle tasks.
2. `runModel.updateMany({ taskId: { $in: bundleTaskIds } }, { $set: { workspaceId: target, updatedBy } }, { session })` re-points runs atomically.
3. **Asset handling decision**: `Asset` carries its own `workspaceId` field (confirmed at `asset.schema.ts:14`) and references `runId` (a Run `_id` string). Assets are re-pointed via `assetModel.updateMany({ workspaceId: sourceWorkspaceId, runId: { $in: runIds } }, ...)` using the run ids gathered in step 1. If no runs existed for the bundle tasks (`runIds` empty), the asset update is skipped.
4. `Run` and `Asset` models are injected into `TransferService` via two new `@InjectModel` parameters, and their schemas are registered in `projects.module.ts` via `MongooseModule.forFeature`.

### Finding D — email-verified gate + shared canCreate helper
`validateTransfer` now accepts an `emailVerified: boolean` parameter (passed from the controller via `userEmailVerified(user)` from `workspaces/guards/create-gate.ts`). An unverified user receives a `ForbiddenException` before any other check. The inline `targetMembership.role === Role.Viewer` check was replaced with the shared `canCreate({ userId, role, canManageKeys: false })` helper.

### Finding C (acknowledged, no change)
The personal-source recheck at the top of `validateTransfer` (source must be `WorkspaceType.Personal`) already rejects a second move with `BadRequestException` because after the first move the project's `workspaceId` is the team's. No change needed.

### Finding E (acknowledged, no change)
`Conversation.originPromptId` is not re-pointed when a prompt moves. Per-user chats stay with the mover's personal account. A code comment was added near the prompt `updateMany` call in `transfer.service.ts` noting this intent.
